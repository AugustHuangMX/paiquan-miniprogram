## 为什么必须是这个架构

微信官方文档写死了两条：

> 「每个微信小程序需要事先设置通讯域名，小程序只可以跟指定的域名进行网络通信」
> 「**域名必须经过 ICP 备案**」

`api.apexlegendsstatus.com` 是境外域名、没有备案，**小程序直接调不了**。
所以中间加一层云函数：

```
微信小程序  →（wx.cloud.callFunction，走微信私有协议，不受域名白名单限制）
云函数 apex →（出网请求，云函数跑在腾讯云里）
api.apexlegendsstatus.com
```

顺带解决了三件事：

1. **不用买服务器、不用买域名、不用域名备案**
2. **API Key 只放在云函数环境变量里**，不下发到客户端 —— 所以别人打开就能用，不用领 Key，也不怕 Key 泄露
3. **上游改字段名时，我改云函数直接部署**，不用重新提审小程序、用户也不用更新版本
   （小程序一旦发布，改一行都要重新审核，所以能把"抗上游变化"的逻辑放服务端就放服务端）

## 排位专区（职业选手的英雄与枪械）

**数据不是从上游接口来的**，而是我们**离线跑 B站直播回放识别**出来的
（识别代码在项目根目录的 `直播识别/`，方法与坑见 `交接说明.md` 第九节）。
所以这一块**不联网、不耗云函数配额**：`onLoad` 里先渲染它，再等分数线那几个请求。

流程：下载回放（720P）→ 每 20 秒抽帧 → 血条定位出三行头像与两个武器槽 →
**同域模板匹配**（模板就从同一段回放里裁，实测同英雄 NCC 0.96~0.98）→ 按局聚合。

| 统计 | 单位 | 说明 |
|---|---|---|
| 英雄选取 | **帧** | 该英雄在抽帧里出现的次数占比 |
| 三人英雄组合 | **局** | 同一局阵容固定，所以按"段"去重后统计局数 |
| 枪械选择 | **帧** | 两个武器槽合并统计 |

⚠️ **两个口径必须写在界面上，否则会被误读**（`T.proCaveat`）：
1. 只统计**主播本人 HUD 上看到的**英雄与武器，**不是全大厅**；
2. 「帧」和「局」单位不同，不能横向比。

**数据文件**：`miniprogram/utils/prostats_data.js`，由 `直播识别/build_prostats.py` 生成，
**不要手改**（改了会被下一次生成覆盖）。视图模型在同目录的 `prostats.js`。

### 布局：三层层次，而不是一长串等权重的列表

2026-10 按用户要求重做过一版（"UI 太丑了"）。原版的问题是**没有层次的密度**：
24 行全是同一种"细条 + 中英名两行"，眼睛找不到入口；三人组合写成
"万蒂奇 + 恶灵 + 罗芭"还会折行；28 张英雄头像完全没用上。

现在自上而下三层（参考国外数据站的通行做法，见交接说明第 14 轮）：

1. **头条卡** —— 最常玩（带头像 + 大号百分比）／最常用搭配／样本量。打开就回答"这人玩什么"。
2. **前五图标卡** —— 英雄头像 + 名次角标 + 名字 + 条 + 百分比。
3. **其余压成一行一个** —— 名次 + 头像 + 名字 + 条 + 百分比，一屏能看完。

三人组合改成**三个头像叠放并排**，名字一行放得下。颜色只做辅助：
百分比和名次都是文字，不靠颜色表意（无障碍要求，`tests/static.test.mjs` 里有用例）。

## 猎杀底分的「涨幅」和「刷新时间」

每张平台卡片下面有两行新东西：

- **`+1,240  较 10-08 18:00`** —— 当前分数线比**约 24 小时前**涨了多少。
  负数是正常的（赛季重置时底分会掉）。**对比的是哪一条会写在后面**，
  否则"涨了多少"就没有参照。
- **`38 分钟前更新`** —— 这是**上游那份数据的刷新时间**，不是"我们什么时候取的"。
  （改之前显示的是取数时间，会被读成"数据是最新的"，属于误导。）

### 为什么涨幅要自己存

上游 `/predator` 只给"当前值"，**没有历史接口**
（实测 `/predator/history` 返回的就是当前值 —— 那个路径被上游忽略了）。
所以只能自己按小时记快照，第二天才有得比。实测上游的刷新时间经常是
**半小时到一小时前**，所以显示"数据时间"这件事本身就有价值。

| 实现 | 位置 |
|---|---|
| 纯逻辑（分桶、挑基准、清理） | `cloudfunctions/apex/snapshot.js` |
| 数据库读写（云开发数据库） | `cloudfunctions/apex/store.js` |
| 涨幅计算（纯函数，网页版共用同一份） | `miniprogram/utils/core.js` 的 `attachPredatorDeltas` |

### 三条必须守住的边界（都写了测试）

1. **没有对比基准 → 整行不显示**，绝不显示成 `+0`（那会让人以为真的一分没动）
2. **基准时间必须落在 20~28 小时前**，否则不算 —— 拿两天前的数据说"昨日涨幅"是错的
3. **数据库任何错误都吞掉降级**（集合没建、权限不对、库卡住）：
   涨幅只是附加信息，**不能让用户连分数线都看不到**

数据库调用还自带 1.5 秒超时：库一旦卡住，宁可不要涨幅，也不能把整次请求拖到云函数超时。

> **网页版没有涨幅**，因为 Netlify 函数是无状态的、没有数据库。
> 那边只显示上游刷新时间，不显示涨幅 —— 这是可接受的降级，不是 bug。

## 英雄选取率（按段位）

> ⚠️ **2026-10-16：这一块已经从战绩页删掉了**（用户要求：排位专区里已经有职业选手的
> 英雄选取 / 三人英雄组合，见 `utils/prostats.js`）。下面记的是当初怎么做的、
> 以及**为什么这么做** —— 服务端的 `cloudfunctions/apex/pickrates.js` 还在，
> 想恢复时不用重新逆向上游，把客户端那两块加回来即可。

**战绩页**曾有「英雄选取率」（2026-10 从猎杀榜页迁过来），四个段位 tab：**全段位 / 白金 / 钻石 / 大师+猎杀**，
每个段位 28 个英雄，显示选取率、涨跌、平均等级。

### 为什么是抓网页，而不是读 API

**上游 API 里没有这个数据** —— 试过 11 个候选端点（`/legends`、`/pickrate`、`/legendstats`…），**全是 404**。
数据只存在于上游**网站**的这几个页面里：

```
/game-stats/legends-pick-rates             全段位
/game-stats/legends-pick-rates/Platinum    白金
/game-stats/legends-pick-rates/Diamond     钻石
/game-stats/legends-pick-rates/Masterpred  大师+猎杀
```

`robots.txt` 是 **`Allow: /`**，明确允许抓取，所以走这条路。云函数 `pickrates.js` 抓这四个页面、
用正则解析出英雄块，缓存 **1 小时**（数据按天变，抓太勤没意义还给人添负担）。

**代价要说清楚**：爬网页比读接口脆 —— 上游改一次页面结构，解析就坏。
所以有两条硬防线（都有测试）：

1. **某个段位解析失败 → 只少那一个 tab**，其它照常
2. **全部解析失败 → 报错、整块不显示**，绝不返回空列表（空列表会被读成"这个英雄没人玩"，是假数据）

### 英雄名的中文译名（口径：用玩家实际在用的叫法）

译名表在 `pickrates.js` 里（**云端一处**，改译名只要部署云函数、不用重新提审）。

**用的是国内社区叫法，不是 EA 营销页那套。** 两套确实不一样，实测对照：

| 英文 | EA 官方简体页面 | 国内社区（本工具采用） |
|---|---|---|
| Octane | 辛烷 | **动力小子** |
| Crypto | 暗码士 | **密客** |
| Caustic | 腐蚀 | **侵蚀** |
| Wattson | 华森 | **沃特森** |
| Rampart | 蕾帕特 | **兰伯特** |
| Vantage | 万塔捷 | **万蒂奇** |

理由：玩家搜的是社区那套。

**两个新英雄用官方名**（社区还没形成叫法）：

- `Sparrow` → **琉雀**（EA 官方帮助页《琉雀指南》）
- `Axle` → **艾克赛尔**（S29 新英雄）

> 网上流传的「轴锋」（博主自译，原文写着"鸭哥这边译为轴锋…欢迎讨论"）和「雀影」（台媒自译）
> **都不是官方名**，所以没采用。

**表里没有的英雄会原样显示英文名**，绝不显示空白 —— 上游出新英雄时一眼就能看出来。
测试里钉死了当前 28 个英雄的译名（漏一个就红），以及"名字不重复"。

### 为什么不做「白金以上」这种累计口径

上游给的是**每个段位单独**（白金页 = 当前段位是白金的人），不是"及以上"。
要算"白金以上"得把各段位的人数加起来，但**分段页面上只有百分比、没有人数字段**，
算不出来。**硬凑一个数就是造假**，所以只做独立段位。

### 排位口径的「三人组合」为什么不做

- **`/game-stats/team-comp` 是个假页面**：兜底页，0 个英雄名、0 个百分比，只有网站框架。
  game-stats 下只有四个真页面（英雄选取率 / 段位分布 / 外观统计 / Steam 统计）
- **也不能从单英雄推算**：三人组合是**强相关**的（玩家会刻意凑特定组合），
  把三个单英雄的选取率相乘在数学上是错的

> 职业赛事口径的三人组合能做 —— 见下面一节。

## 职业热门组合（ALGS 赛事口径）

> ⚠️ **2026-10-16：这一块也已经从战绩页删掉了**（用户要求：排位专区里已经有职业选手的
> 三人英雄组合）。服务端 `cloudfunctions/apex/comps.js` 还在，`比赛` 页那份 ALGS 三人组合
> （来自 `utils/algs.js` 的离线快照）**不受影响、仍然显示**。

**战绩页**曾有「职业热门组合」（同样 2026-10 从猎杀榜迁过来）：**ALGS 职业赛事里最常出现的三人阵容**，
每条带选取率、平均名次、出现场次，只显示最热的前 15 套。

### 数据从哪来

来自上游 **ALGS 赛事页**的「Teams Compositions data」表：

```
/algs/<年-赛季>/<联赛>/<赛区>/Overview     ← 例如 /algs/Y6-Split2/Pro-League/Global/Overview
```

表结构（真实抓到的样子）：

```
Legend                          Pick rate%  Avg. placement  Win Rate%  Top 5 Rate%  Top 7 Conversion Rate%  FWR%  Total occurrences
Caustic, Sparrow, Wraith        45%         10.1            0%         33.3%        0%                       54.8%  9
```

**英雄名复用 `pickrates.js` 里那张译名表**，所以两处译名永远一致。

### 怎么找「最新一届」

抓 `/algs/` 首页 → 抽出所有赛事链接 → 按三层排序：

1. **年份 / 赛季降序**（最新的在前）
2. **赛区优先级**：`Global`（全球大赛）> `APAC_S`（**亚太南部 —— 中国战队所在赛区**）> `APAC_N` > 欧美
3. **赛事级别**：Championships / Playoffs > Pro-League / Open > 其它

然后从最优先的往后试，**第一个有组合表的就用**。新赛季刚开打、页面还是空的时候会
**自动回退到上一届**（有测试守着）。缓存 **6 小时**。

> 赛区优先级是特意这么定的：国内玩家最想看的是亚太南部的职业环境，其次才是全球大赛和欧美。
> 上游真实用的赛区码是 `Global / APAC_S / APAC_N / EMEA / NA / SA`（**下划线**，不是连字符）。

> **冷启动约 6 秒**：要抓的是 2.4 MB 的完整赛事页。这是"首个请求慢、之后 6 小时都走缓存"的性质，
> 而且组合区块在页面最底部，用户滚到那里时通常已经加载好了。真嫌慢可以先用
> `/algs/api/selectionAvailability`（小 JSON）预筛掉没开打的赛事，省掉一次 2.4 MB 抓取。

### 踩过的坑（改这块前必看）

| 坑 | 说明 |
|---|---|
| **`/algs` 必须带尾斜杠** | `/algs` 返回 **301**，而我们的 `fetcher` **不跟随跳转**（`/algs/` 才是 200）。这条卡了整整一轮排查 |
| **`/algs/competitive-meta` 碰不得** | 返回 **403 + Cloudflare 人机校验**（`Checking your browser...`），换浏览器 UA、换子域名都过不去。**这是人家明确的防爬措施，不做绕过** |
| `/algs/game/<hash>` 同理 | 也是 Cloudflare 403。好在赛事页里的组合表够用，不需要它 |
| **overstat.gg 不能用** | 它的 `robots.txt` 写着 **`Disallow: /api/`**，而页面是 Vue 单页应用、HTML 里没有数据。**接口被明确禁止抓取，所以放弃**（尽管它确实有组合分析页） |
| 页面很大 | 完整赛事页 **2.4 MB**（组合表在里面）。带尾斜杠的轻量版只有 438 KB，但**没有组合表**，别图省事 |

### 和「英雄选取率」一样的硬防线

解析失败 / 取不到 → **整块不显示**，绝不返回空数组
（空数组会被读成"职业比赛没有热门组合"，是假数据）。都有测试。

## 比赛专区 · 下一场比赛（2026-10-18）

**比赛页顶部的第一块**：打开就能看到**未来最近一场 ALGS 赛事**的分组和开赛时间；
官方还没排期时**只显示分组**；点队伍弹出队员名单（带国家名与键鼠/手柄标注）。

### 数据从哪来

ALGS 官方赛事页（apexlegendsstatus.com/algs）的**赛事总览页**，服务端渲染，
非浏览器客户端能直接 GET（实测 200）：

| 要的东西 | 页面里的位置 |
|---|---|
| 赛程时间 | 赛程树 `<a class="bracket_match">` 里的 `data-timestamp`（unix 秒）+ `data-match-name` |
| 分组 | bracket 节点 `data-rankings` 里每队的 `groupLetter`（A/B/C/D） |
| 队员 | Playoffs 版总览页的 `playoffs-group-rosters` 区块（按组分列：名字 + 国家 + 键鼠/手柄） |

> **国籍的写法**：中文界面用中文国家名（`中国` / `中国台湾` / `美国`…），英文界面用英文名；
> **台湾一律是「中国台湾」**（英文 `Taiwan, China`），见 `utils/nextmatch.js` 的 `COUNTRY_ZH`。
> 认不出的国家退回上游英文全称，不猜译名。

⚠️ 时间在 `<a>` 的**内容里**（`<div class="bracket_match_scheduled_time" data-timestamp>`），
不在开标签上 —— 只取开标签会把每一场都算成"没有时间"。

生成：

```
node 直播识别/build_next_match.mjs          # -> miniprogram/utils/next_match_data.js（自动生成，别手改）
node 直播识别/build_next_match.mjs --out 直播识别/out/next_match_data.js
```

它扫最近一年（当前是 Y6）的**所有** ALGS 赛事页，挑**开赛时间在未来、且最近**的那一场；
一场未来赛程都没有就直接报错并保留旧快照（不生成"假装还有比赛"的数据）。
视图在 `miniprogram/utils/nextmatch.js`，纯本地、不联网、不耗云函数配额。

### 三个界面决定（都对着 1288rpx 的可视高算过）

1. **赛程用两列格子**，不是"一天一行"：一天三场在 686rpx 里必然折行，四天要 500rpx+，
   会把「分组」挤出第一屏（实测 528rpx）；两列格子 10 场约 300rpx。
2. **分组一次只展开一组**（A/B/C/D 四个标签，各写队数）：40 支队全铺开没法读，
   但"怎么分的、每组分几队"一打开就看得到。
3. **没排期就整块不显示赛程**：只留分组 + 一句「官方还没公布开赛时间，先看分组」；
   名单没公布时写「待公布」，**不编队员**。

### 快照的口径

页面上写「快照更新于 YYYY-MM-DD」，口径说明里写清"官方临时改期/换人不会自动跟着变"。
时间一律是**北京时间（UTC+8）**；倒计时按**打开页面的那一刻**算，过了最后一场显示"赛程已结束"。
测试：`tests/nextmatch.test.mjs`（30 条，含"没排期只显示分组 / 没名单待公布 / 中英双语 / 赛制 / 队标"）。

### 2026-10-26：对照 apexgg.cc 补的四块

用户要求「学习 apexgg.cc，改善比赛分区」。它把赛事做成「头部信息 + 赛制 + 积分/队伍/选手/赛程分页」，
我们只取**在离线快照里站得住**的四样，不硬做没有数据的部分：

| 学到的 | 落到哪 |
|---|---|
| 赛事头要有**日期范围 / 队伍数** | 副标题末尾加 `10/30–11/02`；`4 组 · 40 支战队 · 10 场` 保留 |
| **赛制 / 晋级路径**单独讲清楚 | 赛事页 `info-banner` 的官方英文原文 → 生成时打 `format.key`，视图层翻成 4 条中文路径；**默认折叠**，点开才展开 |
| 每场**谁打** | 从赛程的 bracket 键（`AvB`…）反推「A 组赛程：10/30 01:00 vs B · …」，跟着分组标签切换 |
| 队伍要有**队标** | `tools/build_team_icons.mjs` 把赛事页 40 张队标压成 64×64 PNG（共约 157 KB），队伍卡 36rpx、队员弹层 72rpx |

**故意没做的**：apexgg 的「积分 / 队伍数据 / 选手数据」—— 那些是**赛后**统计，我们的快照里
只有赛前分组与赛程，没有成绩。空表全是「—」，做了反而是假信息。

> **队标是各战队商标**，这里只用于"识别是哪支队伍"。如果审核/法务上有顾虑：
> 删掉 `miniprogram/assets/teams` 并把 `next_match_data.js` 里的 `icon` 置空即可，
> 界面会自动退回纯文字队伍卡（有测试守着"没有图标也能正常渲染"）。

## 小游戏（猜圈练习 + 圈型速判 + 英雄/武器轮盘，2026-10-23）

**第 4 个 tab 从「猜圈」改成了「小游戏」** —— 用户要求把新做的轮盘和猜圈放在同一个分类下，
底下的标签就叫「小游戏」。所以现在那一格是**分类页**（`pages/games/`），
猜圈（`pages/ringguessr/`）、圈型速判（`pages/ringpick/`）、轮盘（`pages/wheel/`）都从它进去。

为什么做成分类页而不是把两个玩法塞进一页：
- 猜圈页是**单屏手势游戏**（`disableScroll: true`、地图要接管 touchmove），
  塞进一页就没法让轮盘滚动，两者会互相打架；
- tabBar 上限 5 个、图标只能用本地文件，以后再加小游戏不该再动底部；
- 多一次点击的代价，换来每个玩法都能有完整的屏幕 —— 它们都不是"取一个数就走"的工具。

### 三个玩法、两种猜圈节奏

| 玩法 | 节奏 | 说明 |
|---|---|---|
| 猜圈练习（`ringguessr`） | 精修：20 秒 + 8 题 | 拖动 / 捏合 / 缩放，把准星拖到位再交卷，按误差计分 |
| 圈型速判（`ringpick`） | 快判：10 秒 + 5 题 | 只点一个字母，四选一，对错分明 |
| 英雄/武器轮盘（`wheel`） | 一次一抽 | 抽英雄 / 三人组合 / 一长一短 / 两把随机 |

两个猜圈玩法**共用同一批真实数据**，但问的不是同一件事：
猜圈练习问"圈心具体在哪"（连续坐标，按距离给分），速判问"圈心往哪个方向走"（离散四选一）。

### 圈型速判：为什么是"四个方向"而不是"四个随机点"

先把 260 局真实序列（上游三圈样本 65 局 + 比赛整局序列 195 局）逐局算了一遍，
发现一件事：**下一个圈全部与当前圈内切** —— 圈心距离恰好等于 `R1 - R2`，260/260 全中。
也就是说"距离"是定死的，唯一不确定的是"方向"。

所以这个玩法只出一种题：**给第一个圈，猜第二个圈的圈心朝哪边走**，四个候选点摆在同一圈半径上。
这样做的好处是四个点**全是合法位置**，不会出现"有一个明显在图外/在圈外"的送分选项。

几个实现决定（都是算过才定的）：

| 决定 | 为什么 |
|---|---|
| 只出「给 1 个圈猜第 2 个」 | 再往后猜时当前圈半径只剩 80~100rpx，四个点会挤在一起、点都点不准 |
| 剔掉 7 道"圆心几乎没动"的题 | 它们的那圈半径只有 79~1100 地图单位，四个点会重叠成一个（题库 260 → 253） |
| 视口放大 1.0~1.9 倍 | 中位距离只有 1635 单位 = 屏幕上 68rpx，四个 96rpx 热区放不下；放大到"候选圈半径 88rpx"后最小间距 101rpx |
| 平移夹在 `[1-z, 0]` | 不夹的话放大后的底图会在某条边露出空白，看起来像"地图缺了一块" |
| 底图不超过 1.9 倍 | 底图是 640×640 的包内图，再放大就糊了 |
| 只判对错 | 四选一没有"差多少分"，但结果里会写"差几个圈半径"，那是信息不是分数 |

一屏预算（子页可用约 1448rpx）：边距 48 + 计分条 93 + 时间条 14 + 题干 47 + 地图 686 + 结果 66 + 按钮 96 + 规则 54 ≈ 1104rpx，不滚动。

### 两个轮盘、四种玩法

| 轮盘 | 玩法 | 怎么抽 |
|---|---|---|
| 英雄 | 抽一位英雄 | 28 位英雄里随机 1 位 |
| 英雄 | 三人英雄组合 | 随机 3 位**不重复**的英雄 |
| 武器 | 一长一短 | 长枪池抽 1 把 + 短枪池抽 1 把（必然不同枪种） |
| 武器 | 两把随机 | 全部 29 把枪里抽 2 把（不重复，可能同枪种） |

**长枪 / 短枪的口径**（国内玩家通行分法，写死在 `utils/wheel_data.js` 的 `CLASSES` 里）：

- 长枪 = 突击步枪 / 轻机枪 / 精确射手 / 狙击枪 → 17 把
- 短枪 = 冲锋枪 / 霰弹枪 / 手枪 → 12 把

### 候选池从哪来（不手抄名字）

`utils/wheel_data.js` **只读 `utils/codex_data.js`**，不自己维护名字表：

- 英雄池 = codex 里的 28 位英雄，中文名 / 英文名 / 头像路径**全都来自那一份**；
  在别处再抄一份，下次识别数据更新（出新英雄、改译名）两边就会打架。
- 武器池 = codex 里的枪械，**去掉投掷刀**（直播识别把它也当"武器"收进来了，它不是枪），
  再按 `WEAPON_CLASS` 标枪种。漏标一把枪 = 那把枪永远抽不到，界面上完全看不出来 ——
  `tests/wheel.test.mjs` 有一条用例专门盯这个。
- 轮盘上的名字用**短标签**（"复仇女神" 而不是 "复仇女神连发突击步枪"）：
  一片扇形的弧长只有五十来 rpx，全名会压到隔壁。全名留给结果卡片。

转盘上只有 2~4 个字的短名字，**结果卡片**才是主角：一位英雄是大卡（108rpx 头像 + 20px 名字），
三人组合 / 两把枪是并排小卡（80rpx 头像 + 13px 名字），下面一行写枪种（"长枪 · 突击步枪"）。

### 转盘是"真转盘"，不是随机延迟闪现

1. **先抽结果，再算角度**：抽到第 i 片，就把它的中线转到正上方的指针下
   （`需要转的角度 = 360 - 中奖片的中线角`，再补 5 整圈）。所以指针停在哪、结果就是哪，
   眼睛能验证 —— 这是 `tests/page.test.mjs` 里那条「指针没对准结果那一片」用例守着的。
2. 动画交给 CSS `transition`（2.6 秒），JS 只给起点和终点；
   **时长必须和 `wheel.js` 的 `SPIN_MS` 一致**，对不上就会"已经出结果了但还在转"。
3. 停下来之后才高亮中奖扇形 + 亮出结果卡片 + 轻微震动（`wx.vibrateShort`，失败不影响逻辑）。

为什么不用"转到随机角度再看落在哪"：那样抽到哪一片取决于动画时长和帧率，结果不可复现，
测试也没法验。

### 扇形为什么用 clip-path + 百分比画

- `conic-gradient` 在 Skyline 渲染器下没有保证，`clip-path` 是 WXSS 明确支持的；
- **`clip-path` 里禁用 `rpx`** —— rpx→px 的编译期替换会把 `polygon()` 参数改坏
  （`docs/design/README.md` 有记载）。所以 29 个扇形的角度全部在 `wheel_data.layout()` 里
  算成**百分比**，WXML 只贴 style。
- 每片圆弧用 4 段折线近似，最大径向误差 < 0.5%，肉眼看不出来。
- 老 iOS WebView 需要 `-webkit-clip-path`，两个都写。

### 一屏预算（对着 1288rpx / 1448rpx 算过）

- 小游戏分类页（tab 页，可用约 1288rpx）：导航 169 + 引言 66 + 两张卡 326×2 + 说明 66 + 边距 48 ≈ 1013rpx，不滚动。
- 轮盘页（子页，没有 tabBar，可用约 1448rpx）：边距 32 + 轮盘开关 80 + 玩法开关 72 + 转盘 600 + 池子 48 + 结果 ~250 + 规则 54 ≈ 1182rpx，不滚动。

### 数值与无障碍

- 字号只用 7 档里的 `--fs-head / --fs-sub / --fs-min`，最小 24rpx（官方下限）；
- 热区：轮盘开关 80rpx、玩法 chip 72rpx 视觉 + 上下各 4rpx 透明热区 = 80rpx、中心按钮 184rpx、整张入口卡可点；
- 对比度（`tools/contrast.mjs` 新加了这几条）：盘面字压在两种扇形底上分别是
  **深色 15.69 / 12.40**、**浅色 17.43 / 15.38**，中奖那片是白字压强调红 **4.85** —— 都过 4.5；
- 旋盘上的"选中"不只靠颜色：**实心强调色 + 白字 + 加粗**三个信号一起用。

## 轮换时间表（展开式）

轮换卡片上有个「展开接下来 24 小时」的按钮，展开是每 15 分钟一格的表。**玩法**和**地图**来源不同：

| 列 | 怎么来的 |
|---|---|
| **玩法**（子弹时间 / 团队死斗 / 控制） | **外推**。它是 **3 场一循环**（45 分钟一轮回），规律有两次独立观察对上：① 用户在 ALS 上看到的连续 5 场；② 上游 API 的 `current + next`。 |
| **地图** | **后台一场一场记**。上游 `/maprotation` 只给「当前 + 下一场」，`next` 是**单个对象**不是数组；加 `date=`/`timestamp=` 参数被忽略；`version=3` 里的 `ltm.rotation` 是空数组（日期停在 2024-11，废弃字段）。所以**没有任何地方能查到或推出未来的地图序列**。 |

### 后台记录器

- 复用**已有的定时触发器**（本来就在跑猎杀线快照），顺手多记一条轮换 —— 不是另做一套定时任务。
- 轮换 15 分钟一场、定时器 5 分钟跑一次 → **每场 3 次冗余，不会漏**。
- 文档 `_id` 用 `模式_开始时间`，**天然幂等**，重复记只会覆盖。
- 保留 3 天，超期自动清。
- 客户端展开时才请求（`action: "schedule"`），不拖慢首屏。

> **上线头一天地图列大部分是「待记录」** —— 那是诚实的：宁可留空也不编。
> 攒够一天后表就是完整的。

**需要在云开发控制台建一个集合**：`rotation_log`（权限用默认的"仅创建者可读写"即可，只有云函数会碰它）。

## 深色 / 浅色主题

左上角语言开关旁边有个 `深色 | 浅色` 开关（英文下是 `Dark | Light` ——
**按钮文字也得跟着语言走**，否则又会变成中英混排），点了整站换主题。

### 实现方式：颜色全部走 CSS 变量

`app.wxss` 顶部定义两套变量（**18 个**），规则里只写 `var(--x)`（**107 处引用**），
**没有任何写死的色值**（白色除外 —— 照片和彩底上的白字两个主题都成立）：

```css
page { --bg: #0d0f13; --card: #171b22; --ink: #e9ecf1; ... }   /* 深色，默认 */
.wrap.theme-light { --bg: #f4f5f7; --card: #ffffff; --ink: #1a1d23; ... }  /* 浅色 */
```

页面根节点挂 `theme-{{theme}}`，切换只是换一个类名 —— **不用重算任何数据**。

### 三个容易踩的坑（都写进测试了）

1. **浅色必须覆盖深色的每一个变量**。漏一个，浅色下那一块就还是深色底。
   `tests/theme.test.mjs` 会列出来。
2. **`color` 必须在 `.wrap` 上再声明一次**（这条最容易漏，已经踩过一次）。
   `page { color: var(--ink) }` 是在 **page 那一层**就把变量算成具体颜色了，
   子元素继承的是**算好的颜色**、不是变量 —— 所以浅色主题改了 `.wrap` 上的变量，
   也救不了那些**自己没写 `color`** 的文字（`.sec-title` / `.plat-rp` / `.pres-name` 等 13 处），
   它们在白底上仍是深色主题那套近白色，**完全看不见**。测试盯着这一行。
3. **彩色文字要换深色版**。深色那套绿 `#3ddc84` 在白底上对比度只有 **1.9**，
   根本看不清 —— 浅色换成 `#0f8a4a` 这种同色系深色版。
4. **原生外壳 CSS 变量管不到**：导航栏、底部 tabBar、回弹那层底色得用
   `wx.setNavigationBarColor` / `wx.setTabBarStyle` / `wx.setBackgroundColor` 改，
   收在 `utils/theme.js` 的 `applyChrome()` 里。
   注意 `frontColor` **只接受 `#ffffff` / `#000000`**（微信的硬性要求）。
5. **主题是全局状态，页面 `data` 里那份是副本**。`data.theme` 在页面模块首次加载时求值，
   之后不再变 —— 所以在别的页面切了主题，切回来必须在 `onShow` 里同步，
   否则又变回旧值（用户报过）。语言是同一个机制，一并同步。

### 一条和语言相同的约束

主题**只存在内存里，不写本地存储**（那条隐私承诺）。所以：切 tab、进页面都不会丢，
**重启小程序回到深色**。

## 中英文切换

三个页面的**左上角**都有一个 `中文 / EN` 开关，点了**整页换语言** —— 不允许中英混排。

### 设计要点

- **词表**：`miniprogram/utils/i18n.js`，`DICT.zh` / `DICT.en` 两套，key 必须一一对应。
- **页面怎么用**：把 `i18n.T(lang)` 整个塞进 `data`，WXML 里写 `{{T.xxx}}`（WXML 不能调函数，这是唯一办法）。
- **动态文案**：`viewmodel` 的各个 builder 都接受可选的 `lang`，**默认 `zh`** ——
  这样网页版、云函数、以及改造前的老测试不传 `lang` 时行为完全不变。
- **段位名**：上游只给英文（`Master`），中文模式下由 `i18n.RANK_CN` 译成「大师/猎杀者/钻石…」，
  否则中文页面里会一直挂着英文段位名。
- **错误文案**：英文模式**不能用云函数返回的那条中文 message**，改成按 `kind` 取英文说明。
- **切换语言不打网络**：各页面把云函数返回的原始数据留在实例上，切换时本地重算。
- **地图名跟着语言走**：中文模式用译名、英文模式用上游原文。
  （曾经写死成 `mapCn || map`，结果**切到英文后满页地图名还是中文**。）
- **原生外壳也要切**：底部 tab 和顶部标题本来写在 `app.json` / 页面 json 里，是**静态中文**，
  只能在运行时用 `wx.setTabBarItem` / `wx.setNavigationBarTitle` 改 ——
  由 `i18n.applyChrome(lang, navKey)` 统一负责，三个页面在 `rebuild()` 里调用。
  页面 json 里的中文标题只是"首屏兜底"，进页面后立刻被覆盖。

### 一条硬约束：语言**不写本地存储**

本项目有一条被测试守着的隐私承诺：**全项目不使用微信的本地存储接口**
（`tests/static.test.mjs`「不保存任何用户数据」）。所以语言只存在内存里：

- ✅ 在页面之间切换、切 tab —— 不会丢（模块在同一个 app 实例里是单例）
- ⚠️ **重启小程序会回到中文**

要改成"记住选择"，就得同时改掉那条隐私承诺（并重新评估隐私指引），**需要产品决策**。

### 防回归（两条自动化检查）

中英混排这种问题靠人肉看是看不住的，所以有两条测试钉着：

1. **英文词表里不许出现任何中文字符**；
2. **三个 WXML 里不许写死中文文案**（去掉注释和 `{{}}` 后，正文只剩空白/标点）。

任何一条破了就红。加新文案时，往 `i18n.js` 里两边各加一条即可。

#### 但真正管用的是「汇总扫荡」

上面两条只管**词表和 WXML**，管不到"云函数返回的中文字段被直接显示出来"这一类 ——
`Monument`、英雄名、段位 tab、生涯条目名、赛区名**全是这么漏出去的**，一个一个人肉找漏了五轮。

所以现在有一条**汇总扫荡测试**：把各个 builder（`buildModes` / `buildStats` / `buildPlayer` /
`buildPredGap` / `buildPredator` / `errView` / 整张英文词表）的**全部显示文本捞出来扫一遍**，
英文模式下出现任何一个 CJK 字符就红。反向也有一条（中文模式下不许混英文单词，
但放过 `PC` / `RP` / `ALGS` 这类专有名词）。

> 2026-10-16：这份名单里原来还有 `buildPickLegends` / `buildPickTabs` / `buildComps`。
> 那三个 builder 随战绩页的「英雄选取率」「职业热门组合」一起删了，名单也跟着去掉。

> **凡是"多语言字段"都要成对给**：云函数同时给中英两套（`name` / `nameEn`、
> `label` / `labelEn`、`region` / `regionEn`），界面按 `lang` 二选一。
> 只给中文的那种，就是下一轮会被用户发现的 bug。

## 同名问题（游戏内 ID 不唯一）

### 同名怎么办

游戏内 ID **不唯一**（Steam 玩家尤其常见），而上游 `/bridge?player=<名字>` 只会返回其中一个账号。
用户反馈过"查到的不是我朋友"。

我实测确认了两件事：

- **上游没有"按名字列出所有同名账号"的接口** —— `/nametouid` 返回 `Player not found`（坏的），
  `/search`、`/players` 都是 404。所以**枚举同名的人做不到**，别去试。
- **但 `/bridge?uid=<uid>` 是可以用的** ✓ 实测直接返回了正确账号。

于是做法是「**用 uid 精确定位**」，而不是去猜：

| 位置 | 行为 |
|---|---|
| 结果面板 | 显示 `UID 2262951949`（长按可复制），让用户能核对到底是哪一个 |
| 分享链接 | 带上 `uid=` —— 好友点开**必定**是同一个账号，不会被同名的顶掉 |
| 输入框 | 直接粘 uid 也能查：**先当名字查，查不到才当 uid 再试一次** |

最后一条是关键设计：因为顺序是"先名字后 uid"，**纯数字的玩家名照样能用**，
不会被"看起来像 uid"抢走；代价只是失败分支上多打一次上游。

### 一个顺手修掉的真 bug

`classifyUpstream` 原来的逻辑是：JSON 正文里带 `Error` 字段时，只处理 429 / 404 / ≥400 三种状态码，
**其它情况会一路落到"成功"**。也就是说如果上游哪天返回 `200 + {"Error":"Player not found"}`，
页面会显示一个叫「未知玩家」的假人 —— 比报错糟糕得多。

实测上游目前用 404，所以这个坑还没被触发，但已经补掉了：
正文里明说 not found 的按 `notfound` 处理，其它带着 `Error` 的一律算失败。

### 为什么是长按复制，而不是加个「一键复制」按钮

> 本来想加个「一键复制 UID」按钮，查了官方《用户隐私保护指引内容介绍》，
> **`wx.setClipboardData` 和 `wx.getClipboardData` 是并列的隐私接口** ——
> 用了就得去后台配隐私指引。为省这一个按钮不值得，改成 `<text user-select>`
> 让用户长按走系统自带的复制：一个 API 都不碰。这条有静态测试守着
> （`tests/static.test.mjs` 里那张禁用接口清单）。

## 地图中文名（怎么改）

上游接口只给英文地图名，而中文客户端显示的是中文，对不上用户会困惑。
对照表在 **`miniprogram/utils/core.js` 的 `MAP_CN`**（云函数用的是同一份）。

**改译名只要部署云函数，不用重新提审小程序** —— 这也是把这张表放在 core.js 的原因。

### 名字来源与核对状态

| 范围 | 中文名 | 状态 |
|---|---|---|
| 六张大逃杀地图 | 诸王峡谷 / 世界尽头 / 奥林匹斯 / 风暴点 / 残月 / 电力区域 | ✅ **已由用户对着游戏逐一核对** |
| 其它模式的据点 | 侵蚀疗法、骷髅镇、哈蒙德实验室、晴雨表、穹顶、熔岩虹吸… | 取自萌娘百科「其它模式地图」列表（同一来源） |
| 列表里没有的据点 | — | **一律保留英文，不收录** |

**宁可显示英文，也不编一个错的中文名** —— 错译会让人以为是另一个地方。
所以 `Monument`、`Thunder Watch`、`Zeus Station`、`Overlook`、`The Core` 这些暂时还是英文。

### 走过的弯路（记下来免得重犯）

一开始我用了 EA 官网 `zh-cn` 页面，但那个链接给回来的**其实是繁体内容**（台版译名：王者峽谷 / 世界邊緣 / 殘月 / 電流區），
不能当国服译名用。后来又把几个据点按字面直译（`Caustic Treatment` 译成「腐蚀剂处理厂」、`Barometer` 译成「气压计」），
对照萌娘百科才发现官方是**侵蚀疗法**和**晴雨表**。

### 漏一条译名，界面上就冒出一个英文名

**轮换模式（Mixtape）用的是"据点"级小地图**（碎片 / 骷髅镇 / 纪念碑 / 晴雨表…），
上游轮着用它们，所以**只要有一个据点没进 `MAP_CN`，中文模式下就会露出一个英文名** ——
用户就是这样看到 `Monument` 的。

两条防线：

1. **去冠词再查一次**。上游对同一张图会写 `Dome` 也可能写 `The Dome`，
   `translateMapName` 查不到时会去掉开头的 `the ` 再查 ——
   否则会出现"同一张图有时中文有时英文"这种最难查的 bug。
2. **`tests/i18n.test.mjs` 里钉了一份清单**（25 个大图 + 据点），
   少一个译名就红。上游以后上新据点，往清单里加一行即可。

> 但**不许为了消掉英文就编译名**：`The Core` / `Zeus Station` / `Runoff` 这些
> 查不到可靠中文名的，仍然按 `tests/core.test.mjs` 那条断言**保留英文**。
> 猜错的名字比露出英文更糟。`Monument`（纪念碑）是社区通行叫法，已从"不许猜"名单移出。

## 踩过的坑（改代码前先看）

1. **绝不能给上游请求带 `Accept: application/json`。**
   上游由 Apache 内容协商提供服务，带这个头返回 `406`，而该响应**没有 CORS 头**。
   网页版曾因此对所有用户显示"网络不通"，实际是请求头把自己坑了。

2. **没绑 Discord 的 Key，上游返回 HTTP 429。**
   照状态码处理会误报"请求太频繁"并无限重试，真实原因（Key 未激活）被完全掩盖。必须先看响应正文。

3. **`/predator` 的真实结构是 `{"RP":{"PC":{"val":…,"foundRank":…}}}`。**
   分组键是 `RP` 不是 `ranked`，分数线在 `val` 不是 `RP`，`foundRank` 是该平台猎杀人数。照文档猜必错。

4. **上游连打时会返回 HTTP 200 + 空数组 `[]`。**
   照单全收会渲染出四张"当前未开启"，让人以为游戏没开任何模式。已用 `isUselessPayload()` 挡掉。

5. **云函数里判断上游成功要用 `r.kind === "ok"`，不是 `r.ok`。**
   `classifyUpstream` 返回的对象没有 `ok` 字段，写成 `if (!r.ok)` 会让**每一次成功请求都被当成失败**，
   而且缓存永不生效。这个 bug 当时是被测试抓出来的。

6. **小程序端不能出现任何外部域名。** `tests/static.test.mjs` 会检查，
   因为境外域名没法加进白名单，上线后必然加载失败。

7. **云函数里不能用全局 `fetch`。**
   微信云开发的 Node 运行时是 **Node 16**，而全局 `fetch` 是 **Node 18** 才内置的。
   真机实测直接返回 `{"ok":false,"kind":"network","message":"运行环境不支持 fetch。"}`。
   网页版那边跑在 Node 20 上一直正常 —— 典型的"换个环境就废"。
   现在统一用 `cloudfunctions/apex/fetcher.js`（只依赖 Node 内置的 http/https/zlib），
   并且有测试会把全局 `fetch` 删掉再验证一遍。

8. **`wx.cloud.init()` 必须显式传 `env`。**
   官方文档把 `env` 标注为**必填**。不传的话小程序端不知道连哪个环境，报
   `-601034 没有权限，请先开通云开发或者云托管` —— 而云函数在控制台里跑得好好的，
   非常容易误判成"云开发没开通"，白折腾很久。
   环境 ID 形如 `cloud1-d8ggx095757c58e20`，在云开发控制台左上角的环境列表里。

9. **云函数上传前要先给云函数目录指定环境。**
   在 `cloudfunctions` **根目录**上右键 →「切换环境」→ 选环境，
   之后才能上传。直接右键某个函数上传会报
   「请选择云函数目录树 (cloudfunctionRoot) 选择一个云环境」。

10. **`project.config.json` 里的 AppID 不能留占位符。**
    留着的话工具能打开项目但编译不了、云开发也用不了，而且不会明说原因。

11. **云函数默认超时只有 3 秒，必须去控制台调大。**
    真机实测报错：`errCode: -504003 | errMsg: Invoking task timed out after 3 seconds`（腾讯云 SCF 的默认值）。
    而实测发现**第一次请求要 4 秒**（新建连接：DNS + TCP + TLS 握手），之后的请求只要 0.5 秒 ——
    冷启动 + 4 秒，3 秒上限根本不够。

    - **控制台**：云函数 → apex → 版本与配置 → 配置 → 超时时间改成 **20 秒**
    - **代码**：`handler.js` 里的 `DEFAULT_TIMEOUT` 设成 8 秒 —— 必须**明显小于平台上限**，
      这样上游慢时是我们主动超时、返回一句干净中文，而不是被平台掐掉、甩用户一坨 `-504003` 英文
    - **`fetcher.js` 开了 keep-alive**：Node 16 默认 `keepAlive:false`，每次请求都重新握手，
      白花几百毫秒。复用连接后第二次起从 4 秒降到 0.5 秒

12. **云函数调用失败的原始报错有 400 多字**（含 callId、trace、文档链接），不能直接给用户。
    `utils/cloud.js` 里按错误码分类（-504003 超时 / -601034 云环境没配 / not found 没部署），
    并统一截断到 60 字。有测试守着长度上限。

13. **`/servers` 里各分组的键含义不一样。**
    `Origin_login` / `EA_novafusion` / `EA_accounts` / `ApexOauth_Crossplay` 的键是**大区**，
    而 `selfCoreTest` 是上游自己的内部服务、`otherPlatforms` 是 PSN / Xbox Live，
    并且 `otherPlatforms` **没有 `ResponseTime` 字段**。
    照大区去遍历后两组，会得到一堆看不懂的行；照固定字段读，会崩。
    （`selfCoreTest` 刻意不展示 —— 那是数据源自身的基础设施，对玩家没有参考价值。）

14. **服务器状态里没见过的状态值必须当成异常，不能当成正常。**
    实测有 `UP` / `SLOW` / `DOWN` 三种。上游哪天加一种写法而我们默认显示绿色，
    就会在服务器真挂掉时给人看一片"全部正常"—— 这是这块最坏的结果。
    现在未知值归到 `UNKNOWN`，计入异常数，界面上写"未知"。

15. **`rankScore: 0` 不是"0 分"，而是"这阶段没打过排位"。**
    上游在 `global.rank.ALStopPercent` 里直接写着 `"No game this split"`；
    而真实打过排位的最低分是 **1**（Rookie IV = 1 分，实测 shroud 的 PS4 档就是这个值）。
    照减法算会显示"距猎杀线还差 20,770 分"，用户只会当成 bug。
    现在 0 分与负分一律不显示差额（已在猎杀榜内的仍显示名次，名次不依赖分数）。

16. **分享链接就是给 tabBar 页面用的，路径带 query 完全可行。**
    `onShareAppMessage` 返回 `/pages/stats/stats?player=xxx&platform=PC`，
    好友打开时 `onLoad(options)` 直接拿到。但参数必须**转义**，解析时还要挡住
    超长与控制字符。有测试守着一条往返性质：**自己生成的链接，自己一定解析得回来**。

17. **「差额」这类派生数字，取不到就整块不显示，绝不用 0 兜底。**
    分数线拿不到时如果退化成 0，界面上会出现"还差 0 分"—— 那是在骗人。
    同理，差额行不显示时不能报错：它只是少一行，主功能必须照常。
